Moving the LCLS Ops drive to a shared drive

A step-by-step guide for moving the folder out of your personal My Drive, so that no file is lost when someone leaves, and no existing link breaks. It comes with this folder: a small toolkit and an AI assistant (Claude) that do the tedious checking for you and explain each step.

Set up (once, about 10 minutes)

  1. Put this folder somewhere it can stay, for example in Documents, and turn on the SLAC VPN.
  2. Open Terminal: press Cmd+Space, type Terminal, press Return. Type cd (with a space at the end), drag this folder into the Terminal window, and press Return.
  3. Type ./gdm setup and press Return. It downloads the tools and Claude Code into this folder, which takes a few minutes, and shows a ✓ for each part.
  4. Only if it asks for a SLAC AI key: paste the key you were given and press Return. Nothing appears on the screen while you paste; that is normal. If you don't have a key, ask the person who gave you this folder. Many SLAC Macs need no key: setup then says you will sign in when Claude first starts.

Setup ends with "Setup is done". If it stops with a ✗ instead, the message above it says why (see Troubleshooting); fix that and type ./gdm setup again. Nothing is installed outside this folder.

Every time

  1. Turn on the SLAC VPN.
  2. Open Terminal, type cd (with a space at the end), drag this folder into the Terminal window, and press Return.
  3. Type ./gdm claude and press Return.

Then tell Claude what you want, in plain words. To begin, just ask "Where do I start?" Later, for example: "Help me with step 1. My folder is <link>.", "Who owns the files that aren't mine?", "Draft the UIT request." Claude knows the plan below and its safety rules, runs the toolkit for you, and explains each result.

In one minute

The risk. Your folder contains files owned by other people. When a person leaves and their Google account is deleted, every file they own is deleted with it, even if it sits in your folder.

The fix. Move everything into a shared drive. Files in a shared drive belong to Stanford, not to a person, so they survive anyone leaving, including you.

The rule that matters. Move, do not copy. A moved file keeps its identity, so every link to it in Confluence, Jira, e-mails and other documents keeps working. A copy is a new file: old links keep pointing at the old one.

The catch. You can only move files you own. For files owned by people who have left, Stanford UIT has to step in, and only while those accounts still exist. That makes the request to UIT the most urgent step.

Why move, not copy

Every Google Drive file has a fixed ID, and every link to it contains that ID: docs.google.com/document/d/1XctqdEbz…/edit. We tested both approaches with real accounts and a test shared drive (full results in Appendix A):

Moved fileCopied file
ID (and therefore every link)same old links open it in the shared drivenew old links still open the old file
Revision historykept 3 of 3 versionslost 1 version left
Commentskept 1 of 1lost 0
"Anyone with the link" sharingkeptnot copied
When the old owner's account is deletedsafe the file belongs to Stanfordold links die nobody is sent to the copy

Rewriting links after copying only works for the links you can find and edit. Links in other people's documents and drives, spreadsheet formulas, e-log entries, e-mails and bookmarks cannot all be found.

B. Google's rules and limits

  • Only the owner of a file can move it from My Drive into a shared drive, unless Stanford allows editors to (Google's "Allow users to migrate files to shared drives" setting). Google's refusal in test T5 named different domains as the reason, which suggests a Stanford editor may be allowed to move a Stanford colleague's file. Step 4's one-file test settles it.
  • Stanford: files owned by someone else can be moved into a shared drive only if the owner is a member of it, or if you have edit access and the owner's account is suspended.
  • Stanford: only Managers of a shared drive can move folders into it.
  • An admin, or a user given the admin privilege "Move any file or folder into shared drives", can move folders including files owned by others.
  • A folder move is refused if 25 or more items, or 10% or more of the items, cannot be moved; or if it has more than 100,000 items; or if the result would exceed 500,000 items or 20 levels of nested folders. Move subfolders separately in that case.
  • Items that cannot be moved are left out: Google puts a shortcut in the shared drive and returns the item to its owner's My Drive.
  • Items owned by accounts outside Stanford can never enter a Stanford shared drive.
  • If a departed user's account is deleted without a transfer, their files are deleted. An admin transfer does not change who has access.

C. Who can see what after the move

  • Members of the shared drive see everything in it, including files that were previously shared with only a few people. Keep restricted material in a separate shared drive or a folder with limited access.
  • People a file was shared with directly keep their access to that file.
  • "Anyone with the link" sharing is kept.
  • People who reached files only through a shared parent folder lose access, unless they are members. That is what folder-sharing.csv from step 1 is for.
  • Editors of the moved folder become Content managers of it.

E. Moving the folder, click by click

  1. Open drive.google.com with your Stanford account and find your LCLS Ops folder.
  2. Right-click the folder → Organize → Move (or drag it onto the shared drive in the left-hand list).
  3. Choose Shared drives → <your shared drive> → Move.
  4. Google warns that sharing will change and that the shared drive's members will get access. That is expected: confirm.
  5. If Google refuses because too many items cannot be moved, move the subfolders one at a time, and check the CSV Google offers to see which items stayed behind and why.
  6. Run ./gdm verify (step 8) afterwards.

Only the files under .sandbox/config/ are secret, and only your account can read them: never share the .sandbox/ folder. Nothing is installed outside the folder, not even Claude Code. Kept outside are only your browser's normal Google sign-in and, on Macs that require one, your Claude sign-in. With a SLAC AI key, Claude's requests go only to SLAC's own AI gateway (ai-api.slac.stanford.edu, reachable on the SLAC network or VPN); with a sign-in, they go where the Mac's IT policy sends them. Either way, it sends no usage statistics, error reports or update checks.

  • Login: ./gdm login opens Google's normal sign-in page. The resulting login is stored in .sandbox/config/, readable only by you. Do not share that folder. The read-only login uses Google's drive.readonly permission, so Google refuses any change made with it.
  • Google requests it makes: list a folder's contents, get one item's details, list sharing (all reads), and copy a file (only for safety-copy, only with --yes). The code that sends requests refuses anything else. See tools/drive_api.py.
  • Tools it installs: ./gdm setup downloads uv (runs the Python scripts), a private copy of Python, and rclone (stores the login), all into .sandbox/. It needs only curl and unzip, which every Mac has; no developer tools.
  • Included skills: SLAC's read-only confluence-search (version 5028e30) and jira-search (version bce9f83) ship in .claude/skills/, so Claude Code finds them on first start. Each has a small added env.local file that points it at the kit's own uv and Python, and keeps your SLAC tokens inside the kit (.sandbox/config/confluence-search/ and .sandbox/config/jira-search/, readable only by you).
  • Google login client: by default the toolkit signs in through rclone's shared Google client, which Google rate-limits and rclone is retiring. For reliability, someone can create a "Desktop app" OAuth client in Google Cloud Console and place its file at .sandbox/config/oauth-client.json; the toolkit then uses it automatically.
  • Installing Claude Code: after installing the tools, ./gdm setup runs install-claude-lcls.sh (also available alone as ./gdm install-claude), a simplified version of the LCLS team's installer (no pass or keyswitch). It downloads the newest Claude Code release from Anthropic into .sandbox/bin/ and checks it against Anthropic's published SHA-256, and writes .sandbox/claude/settings.json from claude-settings.template.json, the settings the LCLS team uses for claude-lcls: auto mode, a one-hour prompt cache, auto-memory off, no experimental features, no non-essential traffic or updates. Then it reads this Mac's IT policy for Claude Code ("managed settings"). If the policy requires a sign-in (forceLoginMethod, as on many SLAC-managed Macs), Claude Code refuses API keys, so the kit sets none and you sign in when Claude first starts. Otherwise it adds the SLAC gateway address and SLAC model names, asks for a SLAC AI key, checks it with SLAC's gateway, stores it in .sandbox/config/slac-ai-key, and asks Claude one short test question. ./gdm install-claude stable installs Anthropic's "stable" channel instead, and ./gdm install-claude 2.1.285 one exact version, such as the one the LCLS team runs on S3DF.
  • Starting Claude Code: ./gdm claude runs only the kit's own copy of Claude Code, with its configuration folder set to .sandbox/claude/ and its temporary folder to .sandbox/tmp/, and ignores any other Claude login, key, gateway or model setting on the Mac. With a SLAC AI key, it first checks that SLAC's gateway answers, and Claude Code reads the key from the kit through its apiKeyHelper setting. It also records this folder as trusted in the kit's own Claude configuration, so Claude does not ask "Do you trust this folder?" (that question starts on "No, exit", which is easy to get wrong).
  • AI guardrails: CLAUDE.md tells an AI assistant the plan and the rules; Claude starts in auto mode, the LCLS team's default: an automatic safety check reviews each action, and Claude still always asks you before safety copies and Google logins, because .claude/settings.json names those, which auto mode honors. The same file blocks it from running rclone, reading the login folder, editing the toolkit or its own settings, running setup or clean, or starting Claude itself.

I. Running the steps without Claude

Setup is described at the top of this page. Two more commands add your SLAC tokens for checklist step 2 (Claude asks for them when needed): ./gdm confluence-login and ./gdm jira-login. Each shows the page where you create the token, then asks for it (hidden input). To update Claude Code later, type ./gdm setup again (press Return to keep the key); ./gdm install-claude stable or ./gdm install-claude 2.1.285 picks a particular version.

When you are finished: ./gdm clean lists what setup put in this folder (programs, Claude's settings and history, your key and logins), asks you to type yes, and then removes it. It keeps results/ and touches nothing in Google Drive, Confluence or Jira. Your Google account still lists the toolkit's access (named "rclone"); you can remove it at myaccount.google.com/connections.

Every step can also be run by hand, without Claude:

./gdm login you@stanford.edu          # read-only Google login
./gdm inventory "<folder link>"        # step 1
./gdm login-writer you@stanford.edu   # step 3: a login that can copy
./gdm safety-copy results/inventory-…/inventory.csv "<Safety copies folder link>" \
    --owners left1@stanford.edu,left2@stanford.edu --outside-org
                                      # step 3: preview; run again with --yes to copy
./gdm verify results/inventory-…/inventory.csv                         # step 5
./gdm verify results/inventory-…/inventory.csv "<shared drive link>"  # step 8
./gdm help                            # all commands
